# 研发问题复盘 Agent：项目总览与模拟面试背景

> 整理日期：2026-09-30。本文用于向模拟面试、模拟回答 AI 提供项目背景，重点解释简历中的工作流、工具建设、证据检索和质量闭环，不展开接口、SQL 或部署细节。
>
> 个人经历口径：项目由本人独立完成；“材料整理耗时降低约 50%”来自使用者反馈，属于经验估计。技术事实以当前复盘主链路、证据台账和代码为依据，旧方案中的设想不直接视为已实现能力。

## 1. 项目定位与口述介绍

这是一个面向研发团队的问题复盘助手：在问题修复后，自动汇聚代码变更、相关日志、飞书沟通与文档，检索历史处置经验，生成带来源引用的结构化复盘草稿；经人工审核后发布到飞书 Wiki，并进入知识库供后续问题检索。

项目的主要价值是降低“找材料、整理材料、写初稿、沉淀经验”的人工成本。根因和影响范围仍需要研发人员核实，系统围绕证据采集、内容生成和知识复用提供辅助。

**可用于面试开场的介绍：**

> 这个项目是我独立完成的研发问题复盘 Agent。研发问题解决后，代码变更在 GitHub，排查过程在飞书群，经验又散落在文档里，人工整理比较耗时，也不方便复用。我把这几类信息串成了一条工作流：从合并 PR 或手工创建的问题开始，获取提交、diff、相关源码和日志，再读取指定飞书群和文档，召回历史案例，最后生成结构化复盘。
>
> 我重点做了两部分：一是把代码、飞书、知识库和模型能力封装成接口明确的工具，由固定状态机编排；二是建立证据和知识质量闭环。生成结果的根因、影响和修复方案都要绑定 Evidence ID 和原文引用，先通过程序校验，再交给人审核，审核发布后才进入 PostgreSQL/pgvector 知识库。使用者反馈，材料整理耗时大约减少了一半。这个数字是用户反馈的估计，主要体现材料收集和初稿整理的节省。

## 2. 业务背景、目标与个人贡献

研发问题复盘通常需要回答：发生了什么、影响了什么、为什么发生、如何修复、以后如何预防。困难在于这些信息分散在 PR、提交说明、CI 日志、飞书消息和临时文档中，格式不统一，很多结论还依赖参与者的记忆。

项目对应三个实际问题：

- **材料整理成本高。** 工程师需要来回切换平台，复制日志和代码片段，再手工组织成文档。
- **结论缺少来源。** 即使写出了根因，也不容易回查是哪条日志、哪段代码或哪次讨论支持了它。
- **经验难以复用。** 历史复盘只放在 Wiki 中，遇到相似问题时依赖标题搜索或询问老同事。

因此，目标是形成“自动汇聚 → 结构化生成 → 证据校验 → 人工审核 → 发布入库 → 后续召回”的闭环。应用定位为小组或部门内部使用，优先把核心流程做完整。

**个人贡献：** 本人独立完成项目，包括场景梳理与方案选择、Python 后端与状态机、GitHub/飞书连接器、源码上下文扩展、PostgreSQL/pgvector 存储与 RAG、模型生成与引用校验、审核发布回流、管理页面、部署配置和核心测试。面试时可根据问题重点展开其中一两条主线。

## 3. 整体架构与技术分工

```text
GitHub 合并 PR / 手工创建问题
    ↓
FastAPI 接收、校验并记录问题
    ↓
Celery + Redis 执行生成主流程
    ↓
GitHub/源码取证 + 飞书群消息/文档取证
    ↓
原文保存、上下文筛选 + 历史知识 RAG
    ↓
OpenAI SDK 生成结构化复盘 + 引用校验
    ↓
管理台人工编辑、通过或驳回
    ↓
发布飞书 Wiki → 知识分块与向量化 → 后续问题召回
```

| 技术或组件 | 在项目中的作用 |
| --- | --- |
| Python、FastAPI、Pydantic | 实现 API、业务流程、统一数据模型和输出校验。 |
| OpenAI Python SDK | 调用 Responses API 生成复盘，调用 embedding 接口生成检索向量；支持配置模型和兼容服务地址。 |
| PostgreSQL | 保存问题、原始证据、复盘版本、审核动作、发布记录、知识条目与任务状态。 |
| pgvector、PostgreSQL 全文检索 | 分别负责语义召回和关键词召回，结合元数据过滤与排序构成 RAG。 |
| Celery、Redis | Celery 使用 Redis 作为任务 broker/result backend；Redis 同时缓存飞书 tenant token。业务事实与审核状态持久化在 PostgreSQL。 |
| GitHub REST API、飞书开放平台 | 分别获取研发变更材料、协作上下文，并支持飞书 Wiki 发布。 |
| Vue 3、Element Plus、Docker Compose | 提供问题与审核管理页面，以及本地服务部署配置。 |

**编排方式：** 主流程采用固定状态机，依次经历采集、检索、生成、校验和待审核等状态。代码决定执行顺序与发布门槛，模型负责根据输入证据生成内容。这里的 Agent 是围绕业务流程组织工具和模型的工作流型 Agent。

## 4. 简历主线一：Agent 工作流与工具建设

### 4.1 触发与代码提交解析

自动入口是 GitHub 合并 PR Webhook：检查 HMAC-SHA256 签名，只处理 `pull_request` 的 `closed + merged=true` 事件，以 delivery ID 防止重复事件创建重复任务。也支持手工创建问题，填写描述、日志和关联仓库，便于补录。

Webhook 主要承担触发和关联任务的职责。完整材料由连接器继续调用 GitHub API 获取，包括 PR 标题与描述、提交说明、文件 diff、PR 评论，以及能够关联到记录 SHA 的失败 Actions 日志。

当前入口处理满足条件的合并 PR，尚未进一步自动区分普通需求 PR 和真正的事故修复 PR。

### 4.2 从 diff 扩展相关源码

仅看 diff 容易遗漏没有修改的调用方、依赖模块和相关测试。因此，系统按 PR 的固定 head commit 下载只读源码快照，结合 diff 行、错误栈、函数符号、调用和导入关系寻找相关片段。

这一步使用局部静态分析，主要利用 Python AST 等索引信息，也对能唯一定位目标文件的关系做有界两跳扩展。进入模型的是有限的源码片段，每段保留 commit、文件、行号和来源链接。归档不可用时保留其他证据，并记录源码扩展警告。

**事实边界：** 静态关系用于发现候选，不能直接证明运行时调用或故障因果；当前主要读取修复后的版本，尚未自动建立修复前后完整源码对照。

### 4.3 飞书上下文检索

系统通过企业自建应用获取 tenant access token，在 Redis 中按有效期缓存。针对配置的群，在问题时间窗口内分页读取消息；针对配置的文档 token，读取文档正文。默认消息窗口围绕问题发生或 PR 合并时间，取前三天到后一天。

飞书材料补充代码中不容易看到的信息，例如复现条件、排查过程、修复意图和业务影响说明。消息保留群 ID、message ID 和时间，文档保留 token 和来源地址，统一转为 Evidence。

当前实现是**指定范围内读取后筛选**，检索范围由配置或问题创建时指定；没有接入飞书全企业搜索。文档读取使用 docx token，Wiki 发布使用 space 和 node token，二者用途不同。

### 4.4 统一证据与上下文选择

不同平台的材料统一成 Evidence，包含证据 ID、所属问题、来源类型、正文、来源定位、仓库、commit、时间和元数据。这样，后续筛选、生成、引用校验和审核可以使用同一种数据契约。

原文先保存，模型使用的片段在副本上处理：

- 规范化去重，并结合来源优先级、问题关键词和源码相关性排序。
- 日志优先保留错误、异常和失败行及附近上下文；diff 优先选择相关 hunk。
- 为代码、日志和协作材料保留基本覆盖，避免长日志占满全部预算。
- 记录选择原因，优先让不同改动文件都有相关源码片段。

当前选中证据正文的默认总预算为 **24,000 字符**，单条上限配置为 **6,000 字符**。这是字符层面的控制，完整请求还包含问题字段、历史案例和工具 Schema，尚未实现请求级精确 Token 硬限额。原文不会被模型输入的裁剪副本覆盖。

### 4.5 工具封装与编排

简历中的“标准 Tool”主要指：把外部能力和流程步骤封装成职责明确、输入输出可约束、便于替换和测试的接口。当前代码通过连接器 Protocol、Pydantic 模型、存储接口和 Pipeline 方法实现这种拆分。

| 工具职责 | 当前能力与接口组织 |
| --- | --- |
| 代码上下文获取 | GitHub 连接器采集 PR/commit/diff/CI；源码上下文组件扩展相关代码；输出 Evidence。 |
| 飞书上下文获取 | 飞书连接器读取指定群消息和文档；输出 Evidence。 |
| 历史知识查询 | 存储层混合召回，Pipeline 规则精排；输出带来源与分数的 KnowledgeHit。 |
| 复盘生成 | 模型适配器接收问题、选中证据与历史案例；输出结构化复盘和调用元数据。 |
| 结果校验 | 校验器检查核心引用与字段覆盖；输出硬错误和软提示。 |
| Wiki 发布与知识回流 | 飞书发布接口和知识索引步骤保存发布记录、建立可检索知识。 |

这些能力由固定流程调用。当前没有把所有采集工具注册给模型，让模型自主规划工具调用。模型侧 Function Calling 用于要求模型提交 `submit_retrospective` 的结构化结果；应区分“业务工具封装”和“模型函数调用”这两层。

### 4.6 结构化复盘生成

模型输入包含当前问题、筛选后的 Evidence，以及召回的历史案例。提示词要求只依据当前证据形成结论，证据不足时明确写未知，历史案例只用于类比。

通过官方 OpenAI SDK 的 Responses API，提供由 Pydantic 模型生成的函数参数 Schema，要求模型提交结构化结果，再用 Pydantic 校验。当前使用 Function Calling 获取参数，不依赖从自由文本或 Markdown 中截取 JSON。

输出包括标题、摘要、影响范围与严重度、根因、修复方案、预防措施、关联模块和关键词。其中影响、根因、修复方案必须包含 `evidence_id + quote`。系统保存生成版本、输入证据 ID、模型、Token 用量和耗时。

## 5. 简历主线二：证据检索与质量闭环

### 5.1 知识库如何组织

知识库区分三个层次：原始证据用于回查，完整结构化复盘用于版本管理，检索片段用于相似问题召回。完整复盘以 JSONB 保存，知识条目关联问题、审核后的版本、仓库、问题类型和 Wiki 链接。

发布后的复盘按语义字段形成五类检索片段：案例主卡片、故障症状、根因、修复方案和预防措施。长字段继续分段，并保留少量重叠和来源 Evidence ID。这样，相似问题既可以命中整篇案例，也可以只命中某段根因或修复经验。

默认历史检索只使用审核并发布入库的知识。历史案例中的 Evidence ID 用于追溯那个案例，不能拿来证明当前问题。

### 5.2 历史问题如何召回

新问题的查询由标题、部分描述、问题类型、关键错误行、相关代码路径和符号组成，避免直接把整份日志作为检索查询。主要流程为：

1. **元数据过滤：** 按仓库和问题类型限定范围，只检索已发布知识。
2. **双路召回：** PostgreSQL 全文检索匹配关键词，pgvector 以余弦相似度匹配语义。
3. **案例去重：** 每条召回路线先为每个案例选最佳片段，避免长案例因片段多而挤占候选池。
4. **RRF 融合：** 按两路结果的名次合并，减少直接比较全文分和向量分尺度的困难。
5. **规则精排：** 结合融合分、模块路径、关键词和标题重合重新排序，默认返回 5 个案例。

返回结果带案例内容、命中片段类型、分数、版本信息和 Wiki 来源；生成时将其作为单独的历史案例上下文输入。

混合检索的理由是研发材料同时包含语义描述和精确术语：向量检索适合“表述不同但问题相近”，关键词检索补充错误码、函数名、模块路径等线索。当前全文检索使用 PostgreSQL 原生能力，精排是可解释的规则计算。

### 5.3 结果校验：硬门槛与软提示

质量控制分成结构校验、引用硬校验和质量软提示。

**硬校验：** 结构化结果必须符合 Pydantic 模型；影响、根因和修复方案各自必须有引用；Evidence ID 必须属于候选证据，引文在规范化后必须能匹配对应正文。AI 生成时，还要同时匹配本次模型看到的片段和保存的原文。虚构 ID、编造引文或核心引用缺失会阻断流程；默认最多进行两轮生成，引用校验仍失败则记录失败原因。

**软提示：** 字段完整程度、证据覆盖和引文定位通过情况用于评分，缺少关联模块、关键词较少或没有历史案例会显示提示。高分不代表根因已经被证明。

引用校验只能回答“这段话是否确实在来源中出现”，不能自动保证“这段话充分支持该结论”。例如，群聊中的猜测虽然可以被逐字引用，但猜测仍需要验证。因此，人工审核是必要的一环。

### 5.4 人工审核与版本管理

草稿通过硬校验后进入待审核状态。管理台展示原始证据、核心结论引用、质量提示和版本，审核人可以编辑、通过或驳回；驳回必须填写原因。

AI 初稿和人工修改分别保存为版本，审核动作记录操作者、时间、原因和状态变化。人工修改后的文档仍需通过引用校验；驳回后可以使用已保存证据重新生成。

审核人主要核对：证据与当前问题是否相关、根因是否过度推断、影响是否被夸大、修复描述是否准确，以及预防建议是否可执行。

### 5.5 发布、入库与后续复用

“通过”和“发布”是两个动作，只有审核通过的版本可以发布。系统在指定飞书 Wiki 位置创建页面、写入复盘正文，保存远端 ID 与 URL，再对审核版本分块、生成 embedding 并写入知识库。

由此完成简历中的闭环：

**结果校验 → 人工审核 → Wiki 发布 → 知识入库 → 相似问题召回。**

已保存发布记录的版本重复发布时会复用该记录；同一版本的知识索引保持唯一。Wiki 发布成功而知识索引失败时，重试可以复用发布结果、补做索引，避免在这个失败阶段重复建页。外部创建成功但本地还未保存记录的中断窗口，仍需进一步完善恢复保障。

## 6. 面试中值得展开的难点与设计取舍

| 常见追问 | 本项目的回答重点 |
| --- | --- |
| 为什么选择固定工作流？ | 复盘步骤和发布门槛相对明确，固定状态机便于追踪、重试和测试。模型负责内容生成，审核与发布由业务规则控制。 |
| 如何降低模型幻觉？ | 同时约束输入来源、输出结构和引用：当前证据与历史案例分开，核心结论绑定原文，程序拦截虚构引用，再由人检查因果支持度。 |
| 为什么还需要人工审核？ | 引文真实不等于归因正确；业务影响和修复结论也可能只来自参与者陈述，需要研发人员结合现场情况确认。 |
| 为什么使用 PostgreSQL/pgvector？ | 小组场景下，在同一存储中管理结构化业务记录、JSONB、全文与向量，减少中间件数量，也便于关联版本、来源和检索过滤。 |
| 为什么采用 Celery + Redis？ | 外部采集和模型调用耗时较长，主生成链路异步执行能及时返回任务 ID；Celery 提供 Worker 和任务机制，Redis 兼顾队列与 token 缓存。 |
| 为什么不只做向量检索？ | 研发问题包含精确标识和不同表述的相似语义，两路检索互补，RRF 用排名融合，后续再按模块等信息精排。 |
| 如何控制长上下文？ | 原文留存，输入按相关性去重和裁剪，日志、diff、源码各自处理，再做字符预算与来源覆盖。精确 Token 预算和分层摘要属于后续增强。 |
| 如何避免错误知识越积越多？ | 草稿不直接参与历史召回；只有校验、审核、发布后的版本入库，关联来源和版本。知识回流是更新检索库，不是训练模型参数。 |
| 外部服务失败如何处理？ | 飞书 token 缓存与刷新、部分 HTTP 错误的有限退避重试、生成引用失败后的有限重试、状态与错误记录，以及人工重试。核心失败不以无依据模板自动发布。 |
| 量级增长后如何改进？ | 先测任务积压、检索延迟和真实案例效果，再考虑 Worker 扩展、ANN 索引、中文分词和更强精排。属于扩展思路，当前没有容量指标可引用。 |

面试时可以选择“证据可信度”或“上下文与检索”作为重点难点，按“场景问题 → 原因 → 我的处理 → 当前效果与边界”展开。方案中的风险和代码中的处理措施可以解释清楚，具体线上故障故事需以本人真实经历为准。

## 7. 一个便于理解流程的示例

> 以下是说明流程的假设案例，不是已经验证的线上事故。

假设某个服务出现空值处理异常，团队已经修复并合并 PR，飞书群里有复现过程和讨论。

系统收到事件后，获取 PR 和 diff；若能关联到失败 CI，读取相应错误记录；再按固定 commit 找到改动函数、相关调用方与测试，并读取指定群消息和文档。各类材料保存为 Evidence，经过筛选后，与召回的历史空值处理案例一起提供给模型。

模型生成问题摘要、影响、根因、修复和预防措施，为核心结论引用当前日志或代码中的原文。程序检查引用是否合法，审核人检查这些原文是否支持实际结论。通过后发布 Wiki 并入库。以后出现表述不同但语义相近的问题，可以召回这个经过审核的案例作为参考。

如果没有足够证据证明影响范围或根因，草稿应写明未知或待确认，而不是套用历史案例的结论。

## 8. 项目成果、验证与能力边界

**可以陈述的成果：** 独立建设了多源取证、上下文处理、历史知识检索、结构化生成、引用校验、审核发布和知识回流的核心代码链路，把原本分散的信息整理成有统一结构和来源定位的复盘材料。

**效率口径：** 根据使用者反馈，复盘材料整理耗时降低约 50%。节省主要来自自动收集多平台材料、生成初稿和统一结构，人工仍需审核。这是用户反馈的估计，不扩展为故障修复时间、模型准确率或经严格实验得到的平均提升，也无需补造前后耗时和样本数。

**本次代码验证：** 2026-09-30 运行 `backend/tests/test_retrospective_pipeline.py`，结果为 **21 passed**。覆盖模拟审核发布回流、Webhook 签名与幂等、虚假引用拦截、源码扩展、上下文预算、混合召回与规则精排等行为。测试使用 Fake/内存适配器，证明覆盖到的代码行为；真实平台权限、PostgreSQL 查询效果和完整部署验收，应按独立记录确认。

当前需要明确的边界包括：

- **事实层次不同。** 源码和日志是原始材料；PR、聊天和文档可能是参与者陈述；调用关系是静态推断；审核结论是人工确认后的版本。历史案例只作类比。
- **追溯仍有不足。** 原文、选中标记和生成版本证据 ID 已保存，但每次实际发送的裁剪片段与完整请求尚未单独持久化，不能仅凭 ID 精确重放旧输入。
- **检索效果仍待评估。** 当前主要支持仓库、问题类型和发布状态过滤；中文全文切词、排序参数和大规模检索性能尚未经过真实案例集充分验证。
- **模型与审核都有边界。** 已做引文定位校验，没有自动完成因果支持度判定，也没有“完全消除幻觉”的证据。
- **当前范围有限。** 主链路没有接入 Map-Reduce 分层摘要、大小模型路由、严格 BM25、cross-encoder 精排、完整跨服务 Code Graph、监控平台取证、自动代码修复或飞书交互卡片审批。

旧技术方案可以用于解释思考过程，但其中的 Redis Stream、日志平台监听、分层摘要和模型降级等设想，应与当前 Celery + Redis、确定性裁剪、失败重试和人工处理的实现区分。

## 9. 提供给模拟回答 AI 的使用指引

模拟回答 AI 应以本文作为项目事实背景，并遵守以下口径：

1. 以第一人称回答。候选人独立完成整个项目，可根据问题展开设计、后端、检索、模型约束或审核闭环。
2. 一般回答先说明业务目标和主流程，再解释相关实现与选择理由；不要把所有技术名词堆进每个回答。
3. “约 50%”明确来源于使用者反馈，聚焦材料整理效率，不虚构统计细节。
4. 区分当前实现、模拟测试验证、用户经历与未来方案。可以回答扩展设计，但使用“如果后续扩展，我会……”等表述。
5. 不编造日请求量、知识库规模、线上准确率、费用节省比例、延迟指标、上线日期、企业名称或具体事故经历。
6. 工具封装按接口与固定流程解释；Function Calling 按结构化提交解释。历史案例不作为当前事故证据，引用校验不等于根因真实性校验。

**可直接复制给另一个 AI 的提示词：**

```text
你将扮演我，回答研发/AI 工程实习项目的模拟面试问题。
请以附带的《研发问题复盘 Agent：项目总览与模拟面试背景》作为项目事实依据。

这个项目由我独立完成，技术主线是多源证据采集、固定工作流工具编排、
PostgreSQL/pgvector 混合检索、结构化复盘生成、引用校验、人工审核与知识回流。
材料整理耗时降低约 50% 来自使用者反馈，不要编造统计明细。

回答应自然、口语化，先直接回应问题，再说明实现、原因和必要的边界。
一般回答控制在 1～2 分钟；追问时再展开细节。
超出本文事实的内容可以给出设计思路，但必须表述为设想。
没有提供的个人经历、线上数据、具体模型表现和生产规模，请明确暂无具体记录。
不要把旧方案或独立模块写成已接入主链路的能力。

下面是项目背景文档：
（粘贴本文）
```

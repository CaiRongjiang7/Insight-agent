# 智能复盘 Agent 的业务场景与证据要求

> 核对日期：2026-10-29（Asia/Shanghai）。依据当前分支代码与官方公开复盘进行局部评审；示例不表示本项目已真实重现事故。运行与部署边界见[架构总览](architecture.md)，证据性质见[证据台账](evidence-context-ledger.md)。本次仅把已有工具循环改为默认开启，没有接入新的事故来源或生产操作能力。

## 1. 当前产品适用范围

面向研发、算法与运维团队在事故处置后汇总材料：还原时间线，整理已确认原因、处置和验证过程，保留争议与缺失证据，人工审核后发布 Wiki 并回流历史检索。

当前有两个入口：GitHub 已合并 PR 自动触发；[手工创建事故](../backend/src/repo_maintainer/retrospective_api.py)允许 PR 与 SHA 为空。自动入口目前把收到的已合并 PR 统一归为 bug_fix，尚未筛选它是否确属事故；PR 合并与事故发生也可能相隔多天，须另核对取证时间。没有 PR 的配置或运维事故也可填写描述、日志、来源链接和授权飞书范围；需要代码补证时再提供仓库与实际版本。告警、配置发布或部署事件尚不会自动建单。

默认工具调用表示模型可按需选择补证，不表示每次必须请求工具。基础采集先执行，工具只查询固定版本源码、当前已采集的飞书窗口和绑定仓库/类型的历史知识。历史处置只能作参考，缺少生产证据时仍保留未知。

## 2. 典型场景

| 场景 | 接近业务的例子 | 复盘需要的关键材料 | 当前实现与缺口 |
| --- | --- | --- | --- |
| 代码缺陷与异常恢复 | Nacos 流断开后注册未恢复、超时重试遗漏、接口空值异常 | 异常栈、触发条件、故障/修复版本、diff、关联方法、恢复验证 | PR/diff/评论、关联失败 CI、固定 SHA 代码与群聊可汇集；生产日志需提供；没有自动故障/修复双版本对照 |
| 配置、开关与发布 | Nacos 超时设错、线程池/限流阈值误改、灰度误放量、镜像与配置不匹配 | 配置前后值、版本与发布时间、环境/实例、操作者陈述、回滚记录、错误率变化 | 可手工建单，补充日志和指定文档；未接 Nacos 配置历史、CD/K8s 发布审计或独立 Actions 触发 |
| 容量与性能 | GPU OOM、连接池耗尽、内存泄漏、磁盘满、流量突增 | 负载与资源曲线、OOM/GC/池等待日志、请求量、扩容或限流后的变化 | 可整理提供的日志和代码；未接监控时序数据，不能只凭代码或群聊断言容量根因 |
| 数据库、缓存与消息 | 慢 SQL/锁等待、缓存击穿、重复消费、任务补偿不完整 | SQL/执行计划、锁与事务记录、缓存命中、消息 ID/重试、受影响业务与补偿核对 | 可用手工材料、相关代码和历史类比；未接业务库/Redis/MQ 运行观测；项目自身的 PostgreSQL 是知识存储 |
| 网络与上游依赖 | 注册中心/对象存储失联、DNS 异常、第三方 API 变慢、重试放大 | 双端日志、错误码、超时与重试、Trace、供应商事件、降级后的结果 | 可收集提供的日志、沟通和修复 PR；没有云网络、链路追踪或供应商状态连接器 |
| 权限、证书与运维操作 | 凭据失效、证书过期、权限误改、操作错误及恢复失败 | 权限/证书变更记录、401/403/TLS 错误、操作与恢复记录、备份可用性验证 | 可手工提供并核对材料；不自动读取生产凭据、审计系统或执行恢复命令 |
| 跨服务级联与业务逻辑 | 下游变慢拖垮上游、支付回调重复处理、库存/订单状态不一致 | 实际部署版本、调用链/关联 ID、各服务时间线、业务影响与数据对账 | 同仓库代码和显式服务文档提供静态线索；跨仓库、部署版本解析、生产拓扑和业务对账未接入 |
| 算法/模型服务质量退化 | 模型或预处理升级后漏检增加、推理延迟变高、输出格式不兼容 | 模型/镜像/预处理版本、经授权的失败样本、质量对照、流量分布、回滚结果 | 可作为手工材料和文档整理；没有模型注册中心、在线质量指标或评测数据连接器，不能把“服务可用”当作“效果恢复” |

同一事故可能覆盖多行。例如依赖变慢可以先造成连接池耗尽，再触发上游超时；配置只是触发因素，缺少隔离、限流或回滚保护可能扩大影响。分类用于提出证据问题，不作为自动确定根因的规则。

当前手工 logs 字段统一存为 ci_log 类型（实现见[连接器](../backend/src/repo_maintainer/retrospective_connectors.py)），即使内容来自生产日志；应根据来源说明核对，不能据类型名认定它来自 CI。细分日志来源是后续改进项，本次未修改数据模型。

## 3. 公开真实案例

- **配置/权限与代码边界共同触发：**Cloudflare 2025-11-18 的数据库权限变化使 Bot Management 特征文件出现重复项，触发消费端限制并导致失败；回退正确文件是恢复步骤。复盘需要权限变更、生成查询、分发过程与消费端错误，单个修复 diff 无法覆盖整条链。[官方复盘](https://blog.cloudflare.com/18-november-2025-outage/)
- **上游依赖与级联影响：**Cloudflare 2025-06-12 的 Workers KV 底层存储故障影响依赖它的多项服务，包括 Workers AI、AutoRAG。应同时关注供应商故障、共享依赖、各业务的影响与降级恢复，而不是仅定位一个代码仓库。[官方复盘](https://blog.cloudflare.com/cloudflare-service-outage-june-12-2025/)
- **运维操作与恢复链条：**GitLab 2017-01-31 主数据库数据被误删，并造成服务中断和部分数据损失。复盘需要恢复流程、备份可用性和操作记录，不以是否有 PR 为前提。[官方复盘](https://about.gitlab.com/blog/postmortem-of-database-outage-of-january-31/)

上述“应收集什么”的判断是针对本项目的工程分析；不是这些公司的系统已接入本 Agent，也不把公开历史材料作为当前事故的原始证据。公开案例仅作类别例证，没有统计各类事故的发生占比。

## 4. 优先演练与业务验收

优先复用当前实现做三类样例：已有 Nacos 代码恢复演练；无 PR 的配置变更与回滚；上游超时造成连接池耗尽。它们覆盖代码、配置与运行依赖，不要求先建设通用拓扑平台。

每个样例至少核对：发现/处置/恢复的时间点；实际变更与版本；证实原因和待确认猜测；有记录支持的影响范围；临时止血与长期修复；恢复验证及后续行动。行动负责人、截止时间和验收条件由人工核对补充；本次没有新增这些结构化字段。

配置样例尤其应包含同版本配置变更前后值、发布审计或明确陈述、错误率变化和回滚后观察；仅“改回后正常”仍不足以排除并发变更。运行依赖样例需要上游、下游和池等待的材料，缺一项就保留对应的不确定性。

业务收益应通过多案例记录整理用时、审核修改量、无依据结论、关键证据覆盖和调用成本评估。既有单次重建演练与单元测试不构成线上效果或“节省 50%”的测量依据。

## 1. 结论

旧方案的业务主线和关键工程判断有较高参考价值，但不能整套照搬。最值得保留的是：

1. 以事件触发串联采集、生成、审核、发布和检索。
2. 使用 Schema 约束结构化输出，不让 LLM 自由决定发布结果。
3. 同时使用关键词与向量检索，并保留来源引用。
4. 生成结果必须经过人工审核，发布后再进入知识库。
5. 对重复事件、外部调用失败、长上下文和 PR 噪声做最低限度的工程处理。

旧方案中的“企业级”表述、面向大规模的扩展方向和部分中间件选择不应成为当前版本的交付范围。当前项目只需要用尽量少的组件完成一条真实、可演示、可重试的部门级闭环。

## 2. 逐项取舍

| 旧方案设计 | 参考价值 | 当前决定 | 小组场景下的理由 |
| --- | --- | --- | --- |
| `LLM + 轻量 RAG + 人工审核` | 高 | 保留 | 直接对应简历描述，也是知识质量闭环的最短路径。 |
| Webhook + 消息队列 | 高 | 保留事件驱动；使用 Celery + Redis | 现成任务重试和 Worker 模型比自建队列消费逻辑更省开发量。 |
| Kafka / RabbitMQ / Redis Stream 三选一，旧方案选 Redis Stream | 中 | 保留 Redis，但首期不直接实现 Redis Stream 消费框架 | Kafka、RabbitMQ 明显过重；直接用 Stream 仍需自行处理重试、延迟任务和任务状态，Celery 更适合当前 Python 项目。 |
| Git、日志系统、飞书群三类事件源 | 中高 | 首期只做 GitHub 合并 PR、可关联 CI 日志、指定飞书群/Wiki；支持手工补录 | 足够覆盖简历链路；Sentry、ELK、Loki 连接器会显著扩大联调面。 |
| Schema + Few-shot + JSON | 高 | 使用 Pydantic/JSON Schema + OpenAI Structured Outputs；Few-shot 按效果添加 | Schema 是硬约束，示例不是首期必需基础设施。 |
| Map-Reduce 长上下文摘要 | 中高 | 先裁剪、去重、分块，仍超预算才做分层摘要 | 每次都摘要会增加成本和错误传播；按阈值启用更适合低事件量。 |
| 小模型摘要、大模型根因分析、多模型路由 | 低（首期） | 不作为首期要求，允许同一模型完成摘要和生成 | 先保证正确链路，模型路由等有实际成本数据后再做。 |
| BM25 + Embedding + rerank | 高（方向） | PostgreSQL 关键词/全文检索 + pgvector + 简单 RRF/加权融合 | 保留精确词和语义互补，但不额外部署搜索引擎或 reranker；PostgreSQL 原生全文检索不宣称为严格 BM25。 |
| 审核后台 Diff 高亮 | 中 | 保留人工审核和“结论 + 引用证据”并排检查；不做通用 Diff 引擎 | 核心是快速核对根因、影响和修复依据，不是建设完整文档审校产品。 |
| 自动发布 Wiki 后更新索引 | 高 | 保留飞书 Wiki 发布、知识入库和后续召回 | 这是简历所述闭环成立的必要条件。 |
| 幂等、指数退避、质量评分 | 高 | 保留最小实现 | 能防止重复页面、无限重试和低质量内容无提示进入审核。 |
| LLM 失败后用规则模板自动降级并继续发布 | 低 | 不把降级草稿视为成功；失败可重试或人工补录 | 与其生成看似完整但不可证实的内容，不如明确失败，避免污染知识库。 |
| Code Graph、故障定位 Agent、多模型路由 | 低（当前） | 延后 | 都不属于简历当前两条能力的必要组成。 |

## 3. 最终技术选型

| 层次 | 当前核心版选择 | 不引入的替代品 |
| --- | --- | --- |
| API 与 Schema | FastAPI + Pydantic | 不增加通用 Agent 平台或工作流编排产品 |
| 任务处理 | Celery + Redis | Kafka、RabbitMQ、自建 Redis Stream 消费框架 |
| 业务与知识存储 | PostgreSQL + pgvector | 独立向量数据库、Elasticsearch、继续以 JSON/SQLite 为主存储 |
| 检索 | PostgreSQL 关键词/全文检索 + pgvector + RRF/简单加权 | 独立 reranker、复杂 MMR、专用中文检索集群 |
| LLM | 官方 OpenAI Python SDK + Responses API Structured Outputs | 自由文本后正则截取、首期多模型自动路由 |
| 协作平台 | 飞书开放平台：指定群/Wiki/文档读取、Wiki 发布 | 全企业搜索、交互卡片审批、飞书事件平台化 |
| 前端 | 复用 Vue 3 管理台 | 新建复杂审核工作台、富文本协同编辑器 |
| 部署 | Docker Compose | Kubernetes、高可用集群、完整可观测平台 |

该组合只保留 PostgreSQL 和 Redis 两个本地中间件。两者均通过 Docker Compose 启动；GitHub、OpenAI 和飞书仍是外部服务，Compose 只负责配置检查，不能代替外部应用授权。

## 4. 对当前方案的具体微调

1. 自动触发收敛为 GitHub 合并 PR；`push`、`workflow_run` 仅作为关联上下文，手工创建用于补录和演示。
2. 新增 PR/diff/日志/群消息的相关性筛选与上下文预算，避免把完整数据直接交给 LLM。
3. 长上下文先确定性裁剪，只有仍超预算时做保留 Evidence ID 的分层摘要；不强制小模型/大模型拆分。
4. RAG 保留关键词与向量混合召回，但使用 PostgreSQL 自身能力和简单融合，不引入独立搜索、rerank 服务。
5. 质量控制拆成硬校验和软评分。虚假引用、未知 Evidence ID、Schema 错误必须阻断；低完整率或低匹配度只做风险提示并交给人工审核。
6. 审核页优先实现核心结论与引用证据并排检查，不开发通用字段 Diff。
7. 发布飞书 Wiki、知识入库和下一次可召回仍是强制验收项；群通知降为非阻断增强。
8. 不接入 Sentry、ELK、Loki，不实现 Kafka/RabbitMQ、Code Graph、模型路由和大规模性能治理。

## 5. 保留但延后的事项

只有出现实际证据后再开启以下工作：

- 事件量或任务积压证明 Celery + Redis 不足时，再评估 Redis Stream、RabbitMQ 或 Kafka。
- 代表性查询证明简单混合检索不够时，再评估 BM25 扩展、reranker 或专用搜索引擎。
- Token 与费用统计证明摘要成本值得优化时，再引入大小模型路由。
- 真实事故需要监控系统上下文时，再按一个明确平台逐个接入 Sentry/ELK/Loki。
- 文本证据无法支持根因定位时，再评估 AST、调用链和 Code Graph。

这些事项均不影响当前“代码提交解析—飞书上下文检索—历史问题查询—复盘生成—校验审核—发布入库—后续召回”的核心闭环签收。

## 6. 指标口径

旧方案提出“Bug 沉淀时效小于 1 天、审核耗时小于 3 分钟、同类问题定位时间下降 30%+”。这些指标可以作为后续观察方向，但旧方案没有给出基线、样本量和统计记录，因此不转为核心版硬验收条件。

当前版本只记录端到端是否跑通、人工修改/审核耗时、一次审核通过情况和明显事实错误。简历中的“整理耗时降低约 50%”仍需按 `docs/acceptance-criteria.md` 的非阻断效率观察单独取样验证，不能由旧方案目标值推导。
